# Data Agent 会话持久化设计

日期：2026-08-07

## 目标

将当前仅存在于 React 内存中的会话状态迁移为按登录用户隔离的服务端持久化。完成后，用户刷新页面、重启前后端、退出后重新登录或在另一浏览器登录时，都能看到自己的最近会话、打开完整历史并继续聊天。

本次只解决会话持久化。模型供应商网络连接问题不在本设计的实施范围内。

## 当前问题

前端 `Workspace` 挂载时创建一个随机会话 ID，并把全部会话和消息保存在组件状态中。左侧“最近”列表也只读取这份内存状态，因此刷新后会生成一个全新的空会话。

后端已经把成功轮次写入 SQLite 的 `sessions` 表，但没有提供会话列表与会话详情接口。现有记录只包含 `role/content`，无法完整恢复回答的 `intent`、SQL、查询结果、分析、执行步骤和错误状态。工具结果还被编码为带有 `Tool result:` 前缀的用户消息，不适合作为新的用户可见消息模型。

## 方案选择

采用服务端 SQLite 作为会话历史的唯一真源。浏览器内存只负责当前页面状态；浏览器存储最多记录当前选中的会话 ID，不保存历史正文。

未采用的方案：

- `localStorage` 无法跨浏览器同步，清理浏览器数据后会丢失，也不适合作为多用户系统的数据真源。
- LangGraph Checkpointer 更适合图执行状态恢复，但不能代替产品所需的会话目录、标题、完整 UI 消息和用户隔离。本阶段引入会增加不必要的复杂度。

## 数据模型

新增 `conversations` 表：

| 字段 | 含义 |
| --- | --- |
| `id` | UUID，会话主键 |
| `user_id` | 会话所有者，来自服务端认证会话 |
| `title` | 会话标题，第一条用户问题的前 18 个字符 |
| `created_at` | 创建时间 |
| `updated_at` | 最近一条消息完成写入的时间 |

在 `(user_id, updated_at DESC)` 上建立索引，用于最近会话列表。

新增 `conversation_messages` 表：

| 字段 | 含义 |
| --- | --- |
| `id` | UUID，消息主键 |
| `conversation_id` | 所属会话 |
| `sequence_no` | 会话内单调递增序号 |
| `role` | `user`、`assistant` 或 `tool` |
| `kind` | `message`、`query_result`、`error` 等展示或内部类型 |
| `content` | 可检索、可传给模型的主要文本 |
| `payload_json` | 完整 UI 数据，如 `intent`、`answer`、`sql`、`result`、`analysis`、`catalog`、`steps`、错误码 |
| `client_message_id` | 客户端为一次发送生成的 UUID，用于幂等去重 |
| `created_at` | 创建时间 |

约束：

- `(conversation_id, sequence_no)` 唯一，保证消息顺序。
- 用户消息的 `(conversation_id, client_message_id)` 唯一，防止重试产生重复提问。
- 所有查询都同时使用 `conversation_id` 和认证得到的 `user_id` 校验所有权；不存在或不属于当前用户时统一返回 404。

## 后端接口

新增以下受认证接口：

- `POST /api/conversations`：创建空会话，返回会话摘要。
- `GET /api/conversations`：返回当前用户的非空会话，按 `updated_at` 从新到旧排列。
- `GET /api/conversations/{conversation_id}/messages`：返回可恢复 UI 的完整消息列表。

现有 `/api/chat` 与 `/api/chat/stream` 继续接收会话 ID，同时增加 `client_message_id`。服务端必须先验证该会话属于当前登录用户。

聊天写入流程：

1. 校验会话所有权。
2. 根据 `client_message_id` 幂等写入用户消息。
3. 调用 LangGraph，并从持久化消息构造最近上下文。
4. 成功时保存完整 assistant payload；查询结果以明确的内部/tool 类型保存，不再伪装成用户消息。
5. 失败时保存 assistant error payload，其中包含可展示说明、稳定错误码和 request ID。
6. 第一条用户消息写入后生成标题；assistant 或 error 写入后更新 `updated_at`。

数据库写入使用事务，避免会话摘要与消息状态不一致。SQLite 连接启用外键检查、WAL 与合理的 `busy_timeout`，降低本地并发写入时的锁冲突。

## 前端数据流

用户登录成功后：

1. 请求 `/api/conversations` 并填充左侧“最近”列表。
2. 如果存在会话，默认打开最近一条并请求其消息；否则停留在空白欢迎页。
3. 点击“创建新对话”时调用服务端创建接口，再切换到新会话。
4. 点击历史项时加载该会话消息，并使用明显的 active 样式标记当前位置。
5. 发送消息时生成一次性的 `client_message_id`。流式增量仍在前端实时展示；收到 `done` 后以服务端返回数据为准更新消息和会话排序。
6. 刷新页面后重新执行上述加载流程，不依赖上一轮 React 状态。

登出时清除前端内存中的会话和消息。下一位用户登录后只能加载其自己的数据。

## 历史数据迁移

保留旧 `sessions` 表，不做破坏性原地修改。

- 只迁移 `user_id` 非空、能够明确关联到现有用户的旧会话。
- 旧 assistant 记录只能恢复文本回答，按 `legacy` 消息降级展示；缺失的 SQL、结果表格和分析字段不伪造。
- `Tool result:` 记录迁移为内部 `tool/query_result` 消息，不显示成用户提问。
- `user_id` 为空的历史大多来自认证功能之前的演示或测试，继续保留在旧表中，但不分配给任何账号，防止跨用户泄露。
- 迁移使用版本化 `schema_migrations` 记录，并在一个事务中执行；重复启动不会重复迁移。

## 异常处理

- 加载会话列表失败：保留主界面并显示可重试提示，不伪装成“暂无最近对话”。
- 加载单个会话失败：显示明确错误并允许返回最近会话列表。
- 模型或工具调用失败：用户消息与错误 assistant 消息都持久化，刷新后仍可看到 request ID 并继续发送。
- 流式连接中断且未得到服务端终态：前端标记“响应中断，可重试”；使用同一 `client_message_id` 重试不会重复写入用户消息。
- 跨用户或不存在的会话：返回 404，不透露该 ID 是否属于其他账号。

## 测试与验收

后端测试覆盖：

- 创建、列出和打开会话。
- 最近会话按更新时间排序，空会话不进入“最近”。
- 两个用户不能互相读取或写入会话，即使使用相同或已知的会话 ID。
- 成功聊天恰好写入一条 user 和一条 assistant 消息。
- 相同 `client_message_id` 重试不会重复消息。
- 模型失败后错误消息可被重新加载。
- SQL、结果表格和分析 payload 可完整往返。
- 旧用户历史只迁移一次；无用户归属的数据不会出现在任一账号下。

前端验收覆盖：

- 发送一轮消息后刷新页面，列表和消息均恢复。
- 重启前后端后重新登录，历史仍存在并可以继续聊天。
- 切换多个历史会话时，内容和 active 状态正确。
- 新消息完成后，会话自动移动到最近列表顶部。
- 登出并切换账号后，不残留上一个账号的会话。
- 对话中的 SQL、数据表格、分析和错误状态在恢复后与首次展示一致。

## 非目标

- 本次不实现会话删除、重命名、搜索、归档和多端实时推送。
- 本次不更改 LangGraph 路由、RAG、SQL 安全策略或模型供应商网络配置。
- 本次不把无用户归属的旧演示历史自动认领给当前用户。
