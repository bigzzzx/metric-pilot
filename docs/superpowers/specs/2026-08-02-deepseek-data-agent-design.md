# DeepSeek Data Agent 设计

## 目标

将当前规则式本地 Data Agent 升级为具备连续对话能力的 DeepSeek 数据分析 Agent。它能回答普通问题，在识别到数据需求时使用受控 SQL 工具查询本地数据，并根据用户意图决定是否对查询结果进行分析。未配置模型或调用失败时，项目仍能使用现有规则模式运行。

## 配置与密钥

- 根目录 `.env` 保存 `DEEPSEEK_API_KEY`，且必须由 `.gitignore` 排除。
- 根目录 `.env.example` 仅提供变量名、官方 API 地址与默认模型，不含真实值。
- 使用 `DEEPSEEK_BASE_URL=https://api.deepseek.com` 和 `DEEPSEEK_MODEL=deepseek-v4-flash`。
- Node 以 `--env-file=.env` 启动，服务端仅从环境变量读取密钥，绝不返回、记录或写入 API 响应、文档或 Git。
- 使用 Node 原生 `fetch` 请求 `/chat/completions`，不引入 SDK。

## Agent 执行流程

1. 前端为浏览器会话生成稳定的 `sessionId`，每个 `/api/chat` 请求携带该 ID、用户消息与最近会话。
2. 服务端检索相关 Catalog 元数据，向 DeepSeek 发送系统提示词、最近 8 轮摘要、受控目录上下文与用户问题。
3. DeepSeek 通过 JSON 输出结构化计划，计划的意图只能是：`CHAT`、`METADATA_QA`、`DATA_QUERY`、`ETL_TRIGGER`、`UNSAFE_REQUEST`。
4. 对 `DATA_QUERY`，模型只能提供一条候选 SQL 与 `should_analyze` 布尔值。服务端继续执行现有 SQL 白名单、单条语句、表名校验与错误纠正，模型不能直接访问数据库。
5. 查询成功且 `should_analyze=true` 时，服务端发送至多 50 行结果、列名、SQL 和问题上下文，DeepSeek 返回简洁的分析、异常或后续追问建议。
6. 对 `CHAT` 直接返回对话回答；对 `METADATA_QA` 使用目录上下文回答；对 ETL 与危险操作继续沿用参数校验和拒绝策略。
7. 返回回答、意图、SQL、结果、可选 `analysis` 与执行步骤。步骤明确标识“LLM 计划”“SQL 安全审核”“查询执行”“LLM 结果分析”。

## 连续对话

后端按 `sessionId` 保存最近 8 轮的最小上下文：用户问题、意图、SQL、结果摘要和最终回答。原始完整结果不进入历史；模型每次收到的结果表最多 50 行。用户可针对前一轮提问“为什么数码最高”或“只看上海”，模型借助历史继续分析或生成新的查询。

## 失败处理与降级

- 没有 Key：使用本地规则规划器，并提示当前为本地降级模式。
- 网络、鉴权或模型服务错误：返回本地规则模式结果与可理解的状态提示，不暴露密钥或原始供应商响应。
- 模型输出无法解析、意图越界、SQL 为空或审核失败：不执行查询；可尝试一次受控修复，否则说明原因。
- 任何模型输出都不能绕过 SQL 安全网关、ETL 参数校验或危险操作拒绝。

## 前端

- 对话页面在“本次执行”中显示 LLM 是否已启用及各步骤。
- 查询回答在模型决定分析时展示独立的“数据分析”卡片；纯查询不增加分析内容。
- 连续聊天复用当前页面会话，刷新页面后生成新的会话 ID。

## 验证

- 通过 mock `fetch` 测试 JSON 计划解析、普通对话、查询、分析、错误输出与本地降级。
- 保留既有目录、SQL 安全、ETL 与拒绝测试。
- 不在自动化测试中调用真实 DeepSeek API。
- 真实 Key 配置后，手动验证一条元数据问题、一条自然语言查询、一次结果分析和一次连续追问。
