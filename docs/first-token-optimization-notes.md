# Data Agent 首 token 响应优化笔记

## 背景与目标

开发时发现，“讲个笑话”这样的简单请求也曾需要等待约 20 秒才能看到回答。目标是缩短首段有效回答的等待时间，减少不必要的模型调用，同时保留多轮上下文、权限校验和数据查询准确性。

## 优化前的问题

简单请求仍可能先经过一次模型路由；生成结果的部分路径需要等待完整结构化内容才能展示。历史上下文、重复检索和重复生成也会增加开销；后续还发现，完整回答缓存即使命中，也可能被同步摘要阻塞。

## 已落地的优化

1. **真实流式输出**：供应商生成的文本增量通过 SSE 直接送到前端，边生成边显示。普通聊天和最终数据分析使用这条路径；SQL 规划等结构化结果仍需完整校验后使用。“正在处理”不算首 token。
2. **缩短简单请求链路**：明确的问候、简短笑话请求用本地规则直接选择通用回答分支，省去一次路由 LLM 调用，也不执行 Catalog、RAG、SQL、ETL。其他问题仍由模型结合当前问题、最近历史和摘要判断，避免把数据追问当成孤立闲聊。轻量分支仍在同一张 LangGraph 内。
3. **控制上下文体积**：原始历史最多取最近 16 条；未被摘要覆盖的已完成消息超过 16 条时，将早期内容压缩，保留最近 12 条原文。随后原文窗口可继续增长至下次摘要阈值。摘要覆盖的旧消息不重复注入，历史记录仍保存在数据库。通用回答也保留历史与摘要。
4. **摘要移出响应关键路径**：用响应结束后的后台任务生成摘要，避免当前回答或缓存命中后仍等待一次摘要模型调用。
5. **减少数据查询开销**：明确物理表的自包含只读问题可跳过模型路由；满足条件时直接定位目录。规划只带相关表结构并去除重复检索片段。简单单值结果（如行数）可由可信查询结果直接组织答案，省去分析模型调用；复杂分析仍交给模型。
6. **分层 Redis 缓存**：缓存工具结果、路由、SQL 计划和分析答案；符合条件的重复问题还可直接复用完整回答，跳过本轮图执行。完整数据答案默认 TTL 60 秒，知识解释默认 300 秒，并设容量和单条大小限制。缓存区分用户、权限和配置；知识解释还关联会话上下文，显式追问等情况绕过。它是受约束的精确复用，不是任意相似问题直接复用。

## 效果与测量口径

- 已有真实模型验收中，普通问候首段文本约 **1.39～1.42 秒**；其中一次记录为首段 1392.86 ms、完整响应 1475.4 ms。
- 原先“约 20 秒”来自等待回答的用户体验描述，并非同模型、同问题、同条件的首 token 基线，不能据此声称严格提升了某个百分比。
- 完整回答缓存命中时，不再调用模型或查询业务表；可通过 `trace.cache.turn_hit=true` 确认。未命中的复杂数据请求仍需检索、规划、执行后才有有效答案，不能承诺都在 1～2 秒内返回。
- 上述是历史测量，本笔记整理时未重新压测。日志已记录节点耗时、模型调用及首次文本耗时，后续可用固定问题集区分冷请求、缓存命中、首段延迟与总耗时。

## 2026-09-20 未缓存三轮验收

使用 DeepSeek V4 Flash，关闭 Agent 路由/计划/回答缓存和工具缓存，连续运行三轮合成 PostgreSQL 验收：

- 完整业务题：每轮 10/10，累计 **30/30**；三轮最低正确率和平均正确率均为 **100%**。
- 同义改写、追问、歧义与权限稳定性题：每轮 12/12，累计 **36/36**；三轮最低正确率和平均正确率均为 **100%**。
- 完整业务题三轮首 token 中位数平均 **9.99 秒**，P95 完整响应平均 **21.19 秒**。
- 稳定性题三轮首 token 中位数平均 **11.12 秒**，P95 完整响应平均 **26.25 秒**。
- RAG 同集最终 Recall@5 **97.44%**、Recall@12 **100%**、P50 **41.71 ms**、P95 **71.88 ms**，无权限泄漏。

这组数据证明当前固定评测集上的准确性已稳定，但模型延迟仍受供应商和问题复杂度影响；它不是生产流量 SLA，也不能替代更大样本和长时间压力测试。

## 面试简述

“我在 Data Agent 开发中遇到简单聊天也要等约 20 秒才看到回答的问题。排查后，从请求链路和展示方式两方面优化：接入 SSE 真流式输出，明确闲聊跳过模型路由和数据工具；用近期消息加摘要控制上下文，并把摘要放到响应之后；针对简单查询减少模型调用，再用带 TTL、权限和配置隔离的 Redis 缓存复用结果。历史验收中普通问候首段文本约 1.4 秒。对数据追问仍保留历史和摘要参与路由，避免为了速度丢失业务上下文。”
